# Data Contract (living)

This doc defines what **ISO-derived game data** we extract and how it is laid out on disk so the C core can load it.

Policy:
- All gameplay-critical numbers come from **game files** (`SSBM.iso` / `_iso/*.dat`) and/or decomp.
- Extracted outputs live under `data/` and are **generated artifacts**. Large or local-only
  extracts are gitignored; tiny runtime-required contract files may be tracked explicitly.
- The C core should load these at initialization (no parsing during `step`).

## Runtime Data Contract: Common Fighter Constants

`data/common/ft_common_data.json` is the tracked, ISO-derived PlCo common-data artifact used for
small runtime-required constants. It is generated by
`tools/extraction/extract_ftcommon_data.py` from `_iso/PlCo.dat`; runtime loads it once during
initialization through `src/common_params.c` and must not parse or allocate from it during frame
steps.

The basic air-to-ground landing callback owns a Wait-vs-Landing split through
`ft_80082B1C` and Fox/Falco `ftCo_AirCatchHit_Coll`. Those callbacks compare
`fp->self_vel.y` to `ftCo_800D0EC8(fp)`, which is computed from:

- `basic_landing_wait_gravity_mult_x30`: `Fighter_804D6524->x30`
- `basic_landing_wait_scale_param_x310`: `p_ftCommonData->x310`

The shared runtime helper is `src/common_params.h::msl_ftco_80082b1c_enters_wait`; callers should
not duplicate `ftCo_CalcYScaledKnockback` or local threshold constants.

The common Fall/FallAerial/FallSpecial animation callbacks also require the hidden pose-blend
constants used by `ftCo_Fall_Anim_Inner`:

- `common_fall_blend_air_drift_threshold`: `p_ftCommonData->x444`
- `common_fall_blend_lerp`: `p_ftCommonData->x448`

Runtime loads both keys through `src/common_params.c`; they are required keys, not optional
fallbacks. Free-running runtime updates the corresponding hidden `mv.co.fall*.x4` blend lane
causally, while one-step reseed reconstructs it from visible action age so BODY/collision pose
sampling can match source on Fall/FallAerial/FallSpecial rows. Source anchors:
`refs/melee/src/melee/ft/chara/ftCommon/ftCo_Fall.c::ftCo_Fall_Anim_Inner`,
`refs/melee/src/melee/ft/chara/ftCommon/ftCo_FallAerial.c::ftCo_FallAerial_Anim`, and
`refs/melee/src/melee/ft/chara/ftCommon/ftCo_FallSpecial.c::ftCo_FallSpecial_Anim`.

## Replay Seed Contract: AttackDash x2340 Countdown

The replay dataset seed contains `attackdash_x0[player]`, the hidden
`fp->mv.co.attackdash.x0` countdown used by `ftCo_800D8AE0` during AttackDash IASA.

Domain:
- `attackdash_x0 > 0` means the source boost-grab pre-gate is still live. If the fighter is in
  AttackDash and source `held_inputs & HSD_PAD_LR` is true, runtime enters CatchDash through
  `ftCo_800D8C54` before ordinary `allow_interrupt` delegation.
- Source `HSD_PAD_LR` is a macro bit produced by `Fighter_Spaghetti_8006AD10`: physical L/R,
  analog trigger pressure, and raw Z can all satisfy it. The current live AttackDash consumer admits
  digital L/R/Z only; analog-only boost-grab remains tied to the separate
  `ftCo_AttackDash_SetMv0` callback-timing owner and must not be widened without that source model.
- `0` means the countdown is absent/expired; runtime must not infer the boost-grab path from the
  button shape alone.

Source/generation:
- `ftCo_AttackDash.c::doEnter` clears `mv.co.attackdash.x0`; `ftCo_AttackDash_SetMv0` later seeds
  it from
  `data/common/ft_common_data.json::attackdash_x0_init_frames`
  (`p_ftCommonData->x68`).
- `ftCo_800D8AE0` consumes or decrements the countdown during AttackDash IASA.
- Slippi exposes `fp+0x2340` as `misc_as`, but public rows can serialize zero for this short
  AttackDash motion-var lane. Preprocessing therefore preserves nonzero `misc_as` when present and
  otherwise reconstructs the entry countdown from the extracted common constant and replay-visible
  AttackDash action age.
- Generated by `tools/slippi/make_dataset_from_slp.py::_derive_attackdash_x0_seed_lane`.
- Runtime consumes the lane in `src/api.c` and `src/locomotion.c`.

Decomp contract:
- `refs/melee/src/melee/ft/chara/ftCommon/ftCo_AttackDash.c::ftCo_AttackDash_SetMv0`.
- `refs/melee/src/melee/ft/chara/ftCommon/ftCo_Attack100.c::{ftCo_800D8AE0,ftCo_800D8C54}`.
- `refs/melee/src/melee/ft/fighter.c::Fighter_Spaghetti_8006AD10`.
- `refs/slippi-ssbm-asm/Recording/SendGamePostFrame.asm`.

The replay dataset seed contains hidden fighter HitCapsule victim-list state used by the C core
during teacher-forced one-step reseed:

- `combat_hitlist_cd[attacker][hit_group][victim]` / `combat_hitlist_victim_iid[...]` are the
  legacy dense group fallback. `0xFFFF` means the victim remains present until the HitCapsule is
  cleared or copied by the hitbox lifecycle.
- `combat_hitlist_hb_valid[attacker][hitbox_id]` marks the per-HitCapsule lane authoritative for
  that exact slot. When this bit is set, runtime materializes `combat_hitlist_hb_cd` /
  `combat_hitlist_hb_victim_iid` and must not fall back to the dense group lane.
- An authoritative per-HitCapsule lane may be non-empty or empty. Empty means the real
  copied/cleared HitCapsule `victims_1` list is empty; it is not permission to consult the dense
  group fallback.

Source/generation:
- Generated by `tools/slippi/combat_history.py::derive_combat_hitlist_seed_fields` and written by
  `tools/slippi/make_dataset_from_slp.py`.
- Runtime materialization is in `src/hitlist.c::hitlist_seed_init_fighter_hitbox_from_group` and
  `src/hitboxes.c` hitbox-refresh ownership.
- BODY-admission seed proof uses the replay-visible `last_hit_by` owner when it names a valid
  current player, and falls back to `last_hit_by_instance` only when the visible owner is unmapped
  or stale. Slippi's visible `last_hit_by` byte can fail to map across same-frame owner
  transitions, while `HitVictim.victim` and `ftColl_80076ED8` are per-fighter-instance state; the
  instance fallback preserves those hidden per-HitCapsule lanes without overriding a different
  valid visible owner.
- GuardSetOff shield-hit onset may be proven from replay-visible hitlag plus shield HP loss even
  when the previous visible action is not Guard-family. In that case seed-history stamps the
  replay-proven per-HitCapsule lanes on the following frozen hitlag rows because
  `ftColl_80076CBC` has already admitted the shield branch and written `HitCapsule.victims_1`.
- Damaging BODY hitlag-tail rows may have previous-capsule geometry and BODY attribution but no
  dense/per-HitCapsule seed row when the offline pose pass cannot reconstruct the victim hurtcaps
  at the accepted-hit boundary. Runtime may reconstruct the missing same-group `victims_1` entries
  during teacher-forced reseed only when frame-start hitlag/hitstun and
  `instance_hit_by`/`last_hit_by` name the current attacker instance/source. Authoritative
  per-HitCapsule empty seeds still block this fallback.
- Accepted AttackAirN shield hits can also seed later no-hitlag Guard-family rows when the same
  AttackAirN source action remains active and the later rows are replay-proven ShieldDesc misses.
  This is still a hidden `HitCapsule.victims_1` owner, not a broad shield suppressor: the bridge
  carries only HitCapsules proven by the accepted shield hit and only while each later row has a
  replay-visible ShieldDesc miss. Because runtime uses `instance_id` as a proxy for vanilla's
  stable victim pointer, preprocessing rebinds the per-HitCapsule victim iid to the current
  Guard-family instance when GuardSetOff releases into Guard.
- Hitbox-vs-hitbox clank contact may be proven from `ftColl_8007699C`-shaped swept HitCapsule
  overlap plus replay-visible clank hitlag on the affected side. In that case seed-history stamps
  the same type-3 `victims_1` entries that `inlineA0`/`inlineA1` write through
  `lbColl_80008688`, so one-step reseeds into the frozen hitlag tail do not re-clank.

Decomp contract:
- `refs/melee/src/melee/ft/ftcoll.c::ftColl_800768A0` copies/clears HitCapsule state on enable or
  hit-group edges.
- `refs/melee/src/melee/ft/ftcoll.c::{ftColl_80076CBC,ftColl_80076ED8}` register accepted shield
  and BODY contacts into active same-group HitCapsules.
- `refs/melee/src/melee/ft/ftcoll.c::{ftColl_8007699C,inlineA0,inlineA1}` register accepted
  hitbox-vs-hitbox clank contact into active same-group HitCapsules with insertion type 3.
- `refs/melee/src/melee/lb/lbcollision.c::{lbColl_8000ACFC,lbColl_80008688}` gate and insert
  `victims_1` entries.

## Replay Seed Contract: GuardSetOff Shield Damage Scalars

The replay seed contains `combat_shield_hit_int_damage[player]` and
`combat_shield_damage_taken[player]` for hidden shield-hit accumulators on accepted GuardSetOff
entries.

Domain:
- `combat_shield_hit_int_damage` is the defender's hidden `fp->x19A4` max integer hit damage for
  the current shield-contact frame. It owns GuardSetOff hitlag and shieldstun/rate.
- `combat_shield_damage_taken` is the defender's hidden `fp->x19A0_shieldDamageTaken` accumulator
  consumed by `Fighter_ProcessHit_8006D1EC` for shield HP depletion. When generated from replay
  shield HP, this is an explicit non-causal teacher-forced one-step lane.
- `0` means unseeded: runtime uses current ShieldDesc/contact geometry and selected HitCapsule
  damage.
- Preprocessing seeds x19A0 only when replay-visible t->t+1 shield HP proves `x19A0 > x19A4`;
  rows where the inferred accumulator is `<= x19A4` remain runtime-selected-contact ownership until
  exact per-HitCapsule shield-contact order is exposed.

Source/generation:
- Generated by `tools/slippi/make_dataset_from_slp.py` from same-frame GuardSetOff + both-fighter
  hitlag proof, replay-visible shield HP drop, shield hold drain, and extracted common shield
  formulas. Replay-visible hitlag is only a lower bound for x19A4 because multiple integer damage
  values can map to the same hitlag count, but extracted active HitCapsule damage is only used as an
  upper source for same-frame special contact owners. Multi-hitbox attack contacts keep the hitlag
  lower bound until exact per-HitCapsule shield provenance is exposed.
- Runtime consumes the lanes in `src/combat.c` only for the current teacher-forced collision frame;
  the frame scheduler clears them after the step. Normal rollouts leave them zero.

Decomp contract:
- `refs/melee/src/melee/ft/ftcoll.c::ftColl_80076CBC`.
- `refs/melee/src/melee/ft/fighter.c::Fighter_ProcessHit_8006D1EC`.
- `refs/melee/src/melee/ft/chara/ftCommon/ftCo_Guard.c::ftCo_80092F2C`.

## Replay Seed Contract: ReboundStop Queued Ground Accel

The replay seed contains `rebound_ground_accel_2_f32[player]` and
`rebound_anim_rate_f32[player]` for hidden values queued by clank ReboundStop entry.

Domain:
- Runtime hitbox-vs-hitbox clank entry computes the value from `dmg.x191C` and extracted
  `p_ftCommonData->{x3D8,x3DC}`, then stores xE8 in the transient lane.
- Runtime also computes `mv.co.rebound.anim_start = (co_attrs.x9C + 0.1) / dmg.x191C` and carries

- `src/physics.c` consumes the lane only on the first Rebound physics frame. That frame uses the
  old `gr_vel` for movement and applies xE8 to post-frame ground velocity, matching

- `src/action.c` consumes the hidden rate when ReboundStop leaves hitlag and when a replay seed
  starts directly on the first Rebound frame.
- `src/fighter_callbacks.c` clears the lane once the fighter leaves ReboundStop/Rebound.
- Normal rollouts do not read replay-derived Rebound xE8/rate seeds after the initial reseed; live
  clank/ReboundStop entry computes the lanes from `dmg.x191C`.

## Replay Seed Contract: Raw Source Port

The replay dataset seed contains `source_port0[player]`, the raw 0-based Slippi/controller port
for each local dataset slot.

Why this exists:
- Local simulator slots are compact (`0..num_players-1`) and follow the selected replay port order.
- Slippi's `last_hit_by` byte mirrors `dmg.x18C4_source_ply` in the raw controller-port domain.
  In two-player replays that use ports such as P1/P3, local attacker slot `1` writes source port
  `2`, not local slot `1`.
- Runtime gameplay ownership, hitlists, combo victim slots, and array indexing remain local-slot
  based. Only replay-facing source-owner writes and source-owner comparisons use `source_port0`.

Source/generation:
- Generated by `tools/slippi/make_dataset_from_slp.py` from the selected `src_ports` list.
- Runtime consumes it in `src/api.c` during reseed and writes source-owner lanes through
  `src/combat.c`, `src/items.c`, and seed hitlist cleanup in `src/hitboxes.c`.

Decomp/recording contract:
- `refs/slippi-ssbm-asm/Recording/SendGamePostFrame.asm` exports `last_hit_by` from
  `dmg.x18C4_source_ply`.
- `refs/melee/src/melee/ft/ftcoll.c::ftColl_80076ED8` and
  `refs/melee/src/melee/ft/fighter.c::Fighter_ProcessHit_8006D1EC` own source attribution after
  accepted contacts.

## Replay Seed Contract: Magnifying-Glass Damage Counter

The replay dataset seed contains `magnify_damage_counter_x1910[player]`, the hidden
`fp->dmg.x1910` counter used by the vanilla offscreen/magnifying-glass damage path.

Domain:
- The counter increments on live fighter states while the player is offscreen in the magnifying
  display, `fp->x221F_b4` is clear, player rules permit magnify damage, and percent is below
  `p_ftCommonData->x7B0`.
- When it reaches `p_ftCommonData->x7AC`, vanilla applies `p_ftCommonData->x7B4` percent-only
  damage with `Fighter_TakeDamage_8006CC7C` and resets the counter.
- `0` means no elapsed offscreen frames; live/non-replay starts build the counter causally.

Source/generation:
- Generated by `tools/slippi/seed_history.py::derive_magnify_damage_counter_x1910` from current and
  prior replay-visible `fp->x221F_b0` rows, `fp->x221F_b4` disable rows, the derived
  `camera_target_point_inside_stage_cam_bounds_u8` predicate,
  contact/action-stable percent deltas, and `data/common/ft_common_data.json` constants.
- The terminal counter value is teacher-forced from `ref_t1.percent` because `Camera_80031144` and
  `Player_GetMoreFlagsBit3` are hidden replay state. Non-terminal rows are backfilled only inside a
  continuous eligible episode that leads to an observed source-shaped magnify tick with no action
  change, no hitlag/hitstun transition, and no visible hit-source attribution change. Offscreen
  camera rows that never show the source-shaped tick keep counter `0`.
- Runtime consumes and updates it in `src/timers.c::timers_update_magnify_damage_post_frame`.
- Because `fp->x221F_b0` also covers match-flow/dead-flow camera-subject visibility, both seed
  derivation and runtime exclude dead/rebirth/entry states from this magnifying-glass approximation.
- Replay-seeded validation rollouts consume a nonzero backfilled counter until it ticks or becomes
  ineligible. Fresh zero-counter starts are blocked from raw replay-visible camera bits alone except
  for the bounded DamageFlyHi/N source-visible owner: runtime must have x221F_b0 live and either a
  horizontal left/right root exit or a camera-target offscreen row whose current horizontal
  knockback trajectory reaches a side camera bound within one x1910 damage interval. Vertical/top
  exits with no side-bound trajectory and DamageFlyLw/Top/Roll rows remain negative controls
  because their replay-hidden hit pose can differ from the lightweight visible-pose reconstruction;
  those rows may only consume already-seeded nonzero x1910 episodes.
  The RL1 profile intentionally ignores the camera-box visibility bit, so the explicit hidden
  counter/source-owner pair is the rollout owner for magnify damage, not raw
  `state_flags[4]&0x80`.

Decomp/data contract:
- `refs/melee/src/melee/ft/fighter.c::Fighter_procUpdate`.
- `refs/melee/src/melee/if/ifmagnify.c::{ifMagnify_802FC998,ifMagnify_802FB6E8}`.
- `data/common/ft_common_data.json::{
  magnify_damage_interval_frames,magnify_damage_percent_limit,magnify_damage_amount}`.

## Replay Seed Contract: Pending Rebirth Fighter Kind

The replay dataset seed contains `match_flow_pending_rebirth_char_id[player]` for 4-player
team-stock / inter-stock rows where Slippi serializes the waiting DeadDown slot as
`char_id=0, stocks=0` until Rebirth becomes visible.

Domain:
- Nonzero means the source match-flow owner still has a pending fighter kind for a DeadDown row
  whose `match_flow_timer` is counting down to Rebirth.
- Runtime consumes it only at the Dead* -> Rebirth transition; earlier DeadDown rows remain
  replay-visible zeroed slots.
- `0` means no pending Rebirth owner; zero-stock zero-char DeadDown remains an eliminated terminal
  slot.

Source/generation:
- Generated by `tools/slippi/make_dataset_from_slp.py` from game-start player static character data
  plus prefix-causal `match_flow_timer`/DeadDown rows, requiring teams context, a same-team stock
  share source (`stocks > 1`), and visible transition/continuity into the zeroed pending state.
- Runtime consumes it in `src/match_flow.c` after the countdown reaches zero.

## Doubles Validation Domain: Team Attack ON

The initial doubles validation lane is explicitly Team Attack ON only:

- Four-player suite JSON must declare `"team_attack_on": true`; suite loading rejects 4-player
  suites without that contract.
- Four-player teams preprocessing also checks the Slippi game-start bitfield and rejects Team
  Attack OFF/unknown replays instead of silently evaluating them under the simulator's friendly-fire
  combat rule.
- This is a validation-domain guard, not a runtime gameplay bridge. Team ids remain match-flow and
  observation state for the supported doubles lane.

## Replay Seed Contract: Staling History

The replay seed contains fighter attack identity (`attack_id`, `attack_instance`) plus the
per-player stale queue (`stale_queue_index`, `stale_move_id[]`, `stale_attack_instance[]`).

Source/generation:
- `tools/slippi/staling_history.py` reconstructs the prefix-causal stale tables from replay history.
- Action-state transitions use the extracted MotionState move-id table and mirror
  `ft_800890D0`.
- Fox/Falco SpecialN Loop -> Loop restarts are visible as same-action SpecialNLoop instance-id
  changes with action-frame reset; they run `ftFx_SpecialN_OnChangeAction -> ft_800892A0`, which
  bumps `fp->x206C_attack_instance` for the current move id so repeated laser hits do not collide
  under stale-table duplicate suppression. The separate hidden loop-repeat latch is carried by
  `seed_t.specialn_blaster_loop_requested`; do not infer it from generic instance ordering.
- Reflected/projectile item hits use the item-owned stale path when `last_hit_by_instance` matches a
  unique item row: the item's current owner selects the stale table, while the item
  `attack_id`/`attack_instance` provide the `(move_id, instance)` pair. The previous post-frame item
  row is consulted first because the damaging hit can destroy the item before the damage post-frame
  is serialized.

    Decomp: `refs/melee/src/melee/ft/chara/ftCommon/ftCo_Guard.c:211-239`.

Simulator usage:
- `shields_refresh()` uses this table to compute a **world-space** shield bubble center `(x,y,z)` for debug geometry
  and shield-vs-body precedence in debug combat contact classification.
- This is **suite-neutral**: it does not mutate fighter state, and it does not affect validated compare outputs.

Binary layout (little-endian):
- Header:
  - `magic[8] = "MSLSHLD1"`
  - `version: u32 = 4`
  - `frame_count: u16` number of timeline frames stored (typically `round(fig.frames)+1` for msid 38; Fox/Falco is 371)
  - `neutral_frame: u16` guard tilt neutral frame (decomp: `mv.co.guard.x8` initial value; typically 10)
  - `guard_on_x20_xyz: 3 * f32` fresh entry target from `ftData.x20->x0->x8`
  - `guard_on_frame_count: u16`
  - `pad: u16`
- Payload:
  - `xyz: frame_count * 3 * f32` (packed as `[x0,y0,z0, x1,y1,z1, ...]`)
  - `guard_on_xyz: guard_on_frame_count * 3 * f32` live GuardOn submotion trajectory

Coordinate semantics:
- Each `(x,y,z)` is the translation component (`tx,ty,tz`) of the shield joint's **fighter-local** transform under
  the `ftCo_SM_Guard` (msid 38) tilt timeline, evaluated at integer frame `f`.
- These coordinates share the same fighter-local convention as SSANIM01 matrices (`data/anims*.bin`) (TransN/root translation removed).
- `shields_refresh()` consumes them as follows:
  - Compute a target tilt frame from stick direction:
    - `rad = atan2(stick_y, stick_x * facing_dir)` in `[0, 2π)`, then `deg = clamp(rad * 180/π, 0..359)`.
    - `tilt_frame = clamp(neutral_frame + deg, 0..frame_count-1)`.
  - Blend between neutral and angled offsets by stick magnitude `mag = clamp(sqrt(x^2+y^2), 0..1)`:
    - `d = neutral_xyz + mag * (tilt_xyz - neutral_xyz)`.
  - Apply per-fighter runtime scale: `d *= fighter_scale_y` (uniform scalar).
  - Convert to world space: `world = (pos_x, pos_y, 0) + (d.x * facing_dir, d.y, d.z)`.
- Fresh GuardOn / GuardReflect entry snapshots currently consume `guard_on_xyz[0]` with the same
  facing / model-scale policy. Stale v1-v3 tables are rejected because their optional
  `guard_on_x20_xyz` payload was either absent or extracted from the wrong root object.

## `data/hurtcaps/<char>.bin` (MSLHURT1 v1)

Purpose: compact, init-time-loadable tables for fighter hurt capsule init records (`ftHurtboxInit`).

Decomp semantics:
- Init struct: `struct ftHurtboxInit` in `refs/melee/src/melee/ft/chara/ftCommon/types.h`.
- Application: `ftColl_HurtboxInit` in `refs/melee/src/melee/ft/ftcoll.c` copies the record into a
  `FighterHurtCapsule` / `HurtCapsule` and binds the capsule to a bone via:
  `hurt->capsule.bone = fp->parts[hurt->capsule.bone_idx].joint`.
- Endpoint positions are later computed from the bone transform + offsets (see `lb_8000B1CC` usage in
  `refs/melee/src/melee/lb/lbcollision.c` around `checkPos` / `lbColl_80008248`).

Binary layout (little-endian):
- Header:
  - `magic[8] = "MSLHURT1"`
  - `version: u32 = 1`
  - `capsule_count: u16`
  - `reserved: u16 = 0`
- Records (`capsule_count` entries), each:
  - `bone_part_id: u16`
  - `height: u8`
  - `is_grabbable: u8`
  - `pad: u16 = 0`
  - `a_offset: 3 * f32`
  - `b_offset: 3 * f32`
  - `scale: f32`

Field semantics:
- `bone_part_id` is `ftHurtboxInit.bone_idx` (decomp type `Fighter_Part`; `refs/melee/src/melee/ft/forward.h`).
  This is the same id domain as SSANIM `joint_parts` entries and must be passed as `part_id` to
  `anim_pose_get_matrix(...)` in the sim.
- `a_offset` / `b_offset` are the local-space offsets copied into `HurtCapsule.a_offset` / `b_offset`.
- `scale` is copied into `HurtCapsule.scale` (treated as capsule radius in collision code).
  Note: vanilla sometimes applies additional per-fighter scale factors (e.g. `fp->x34_scale.y`)
  when deriving bounds from hurt capsules (`refs/melee/src/melee/ft/chara/ftCommon/ftCo_0A01.c::ftCo_800A0DA4`).
  The sim models this as `MslSeed.fighter_scale_y` / `MslStateSoA.fighter_scale_y` and applies it
  to pose-derived world endpoints and radius.

## `data/hitboxes/<char>.bin` (MSLHITB1 v1)

Purpose: compact, init-time-loadable hitbox event tables (movescript-derived) keyed by submotion id.

Current simulator usage:
- Loaded at init only (no parsing/allocations on the per-frame hot path).
- Used to compute pose-driven **world-space hitbox centers** and HitCapsule attributes for combat,
  shield/BODY contact debug readback, and hitbox-vs-hitbox clank.
- Common extracted moves include attack, throw, escape, guard, RunBrake, and CliffAttackSlow/Quick
  submotions for both Fox and Falco. Character-special hitbox timelines live in
  `specials_by_msid` in `data/moves/<char>.json` and are packed into the same binary table.
  Extraction must not hide real per-character move data to avoid validation rows.

Binary layout (little-endian):
- Header:
  - `magic[8] = "MSLHITB1"`
  - `version: u32 = 1`
  - `entry_count: u32` number of index entries
- Index (`entry_count` entries), each:
  - `msid: u16` submotion id / Slippi post-frame `animation_index` (lower 16 bits)
  - `rec_count: u16` number of event records for this msid
  - `rec_bytes: u32 = rec_count * 44`
  - `payload_off: u32` absolute byte offset to this msid's first event record
- Records (`rec_count` entries), each 44 bytes:
  - `frame: u16` integer timeline key (interpreted against seeded `action_frame`)
  - `kind: u8`:
    - `0`: create/set-enable (`ftAction_8007121C`)
    - `1`: clear (`clear_hitboxes`, or `hitbox_id==0xFF` clear-all)
    - `2`: active-slot damage mutation (`ftAction_8007162C`) with no create-edge side effects
  - `hitbox_id: u8` slot id (0..3 typical). If `kind==1` and `hitbox_id==0xFF`, this is a clear-all record.
  - `bone_part_id: u32` fighter part id (same domain as SSANIM `joint_parts`; pass as `part_id` to
    `anim_pose_get_matrix(...)`).
  - `x: f32`, `y: f32`, `z: f32` bone-local hitbox center offset, stored in **HitCapsule.b_offset**
    component order (not raw script field names). Decomp mapping at hitbox creation:
    - `b_offset.x := z_offset`
    - `b_offset.y := y_offset`
    - `b_offset.z := x_offset`
    refs/melee/src/melee/ft/ftaction.c::ftAction_8007121C
  - `radius: f32`
  - `damage: f32`; for `kind==2`, the new active-slot damage value.
  - `u16_tail[8]: 8 * u16` additional extracted fields (decomp-shaped):
    - `u16_tail[0]`: `angle` (0..361; 361 is Sakurai angle sentinel)
    - `u16_tail[1]`: `kbg` (knockback growth)
    - `u16_tail[2]`: `wsk` (weight set knockback)
    - `u16_tail[3]`: `bkb` (base knockback)
    - `u16_tail[4]`: `element` (low 8 bits) and `shield_damage` (high 8 bits, 2's complement `s8`)
    - `u16_tail[5]`: `sfx_severity` (low 8 bits) and `sfx_kind` (high 8 bits)
    - `u16_tail[6]`: bitfield of boolean flags:
      - bit 15: `rebound`
      - bit 14: `clank`
      - bit 13: `ignore_fighter_scale`
      - bit 12: `ignore_thrown_fighters`
      - bit 11: `item_hit_interaction`
      - bit 10: `hit_aerial`
      - bit 9: `hit_grounded`
    - `u16_tail[7]`: hitlist metadata pack (decomp-shaped):
      - low 8 bits: `rehit_rate_frames` (decomp: `HitCapsule.x40_b4`; 0 means "indefinite until cleared")
      - bits 8..10: `hit_group` (decomp: `spawn_hitbox_0.hit_group` / `HitCapsule.x4`)
      - remaining bits: reserved (0)
      - note (current extraction): for **fighter** hitboxes we currently always emit `rehit_rate_frames = 0` because no GALE01
        fighter-side writer for `HitCapsule.x40_b4` has been identified yet; **item/projectile** hitboxes may populate this field.

Runtime semantics (current C-core policy):
- Events are applied in file order up to `frame` to derive the current active hitbox definition per `hitbox_id`.
- Fighter hitbox radius and local offsets are scaled with GALE01's single-precision
  `ftAction_804D82A0` literal (`.float 0.003906`), not the exact rational `1/256`. This matters
  for near-boundary `ftColl_80076ED8` phantom/tip-log rows where `HitCapsule.coll_distance` is
  compared against `p_ftCommonData->x7A8`.
- Fighter BODY phantom/tip-log selection uses the concrete active HitCapsule. The authored
  same-group primary is identified from active MSLHITB1 `damage`, `hit_group`, and source HitCapsule
  id/order fields and stays on the full BODY path; later/equal siblings and lower-damage same-group
  limb capsules may take the `checkTipLog` / victims_2 branch when `coll_distance < x7A8`.
- Same-action grounded Attack* restarts use MSLMSO01 grounded-attack class ownership for
  `Fighter_ChangeMotionState -> ftColl_8007AFF8 -> ftColl_800768A0` clearing copied HitCapsule
  lists. This is not a Fox/AttackHi3-only replay slice; non-grounded AttackAir states do not
  consume that clear owner.
- Pose lookup failures for a specific hitbox skip that hitbox only (do not affect anything else).
- World-space center is pose-driven and uses the same conventions as hurtcaps/shields:
  - `center_local = (pose_mtx * (x,y,z)) * fighter_scale_y * co_attrs.model_scaling`
  - `center_local = rotY90(center_local, facing_dir)` using the decomp-shaped root-part facing rotation
    (`x' = facing_dir * z`, `z' = -facing_dir * x`)
  - `world = (pos_x,pos_y,pos_z) + center_local`
  - `radius *= fighter_scale_y` unless `ignore_fighter_scale` is set (hitbox flags bit 13);
    radius does **not** get `co_attrs.model_scaling`.
  - Source/runtime references: `refs/melee/src/melee/ft/fighter.c::ftPartSetRotY` and
    `Fighter_UpdateModelScale`, `refs/melee/src/melee/ft/ftanim.c::ftAnim_8006FA58`,
    `refs/melee/src/melee/ft/ftcommon.c::ftCommon_8007F6A4`, and `src/hitboxes.c`
    HitCapsule center/radius materialization.

Damage hitlag-exit DI math:
- `ftCo_Damage_OnExitHitlag -> ftCo_8008E5A4` consumes the prior-frame input snapshot before
  current-frame `Fighter_procUpdate` input refresh, then rotates `x8c_kb_vel` through GALE01's MSL
  `atan2f`/`sinf`/`cosf` path and PPC fused projection/angle operations.
- Runtime keeps this as source-order gameplay math in `src/timers.c`, not a seed lane. It applies
  only on the source post-hitlag callback boundary (`hitlag_pre_timer != 0 && hitlag == 0`) and
  does not change grounded xF0-owned slide velocity.
- Source paths: `refs/melee/src/melee/ft/fighter.c::{Fighter_8006A1BC,Fighter_8006D10C,Fighter_procUpdate}`,
  `refs/melee/src/melee/ft/chara/ftCommon/ftCo_Damage.c::{ftCo_Damage_OnExitHitlag,ftCo_8008E5A4}`,
  `refs/melee/build/GALE01/asm/melee/ft/chara/ftCommon/ftCo_Damage.s::ftCo_8008E5A4`,
  `refs/melee/src/MSL/trigf.c::{sinf,cosf}`.

## What the C core should load (minimum)

To avoid “mystery drift”, prefer loading the following early:
- **Stage collision**: segments + ledge flags + platform flags + a stable `ground_id` mapping.
- **Fighter attributes**: gravity/terminal velocity, traction/friction, jump velocities, ledge snap params, ECB joints/offsets.
- **Move event tables**: hitbox/hurtbox state changes, IASA/interrupt windows, articles (laser), throw flags, etc.
- **Animation attachment data**:
  - Either (A) full per-bone matrices per frame for the bones we need, or
  - (B) precomputed per-frame attachment transforms for hitboxes/hurtboxes/ECB sources.
  - The extractor currently outputs (A)-style matrices in `data/anims/*.bin` for Fox/Falco, and a broader-coverage variant in
    `data/anims_ecb/*.bin` used only to generate ECB tables.

`ground_id` semantics (current assumption):
- Our datasets store `ground_id` directly from Slippi post-frame `ground` (see `tools/slippi/make_dataset_from_slp.py`).
- The simulator treats `ground_id` as the **stage collision segment/line index** from the stage’s collision table.
  - For Final Destination this matches the ISO-extracted indices in `data/stages/final_destination.json` (`segments[].i`), e.g. the main floor uses segment indices `0`, `1`, and `2`.
  - If we discover a stage-specific remapping (decomp / Slippi schema clarification), update this note and the stage loader accordingly.

## Schema notes / stability

This project avoids explicit “versioning” in naming. Instead:
- Generated files should include enough **self-checks** (magic strings, record sizes, offsets) to fail loudly when incompatible.
- Contract changes should be reflected here immediately, and extraction scripts updated accordingly.
